# ADR-006: Client API and session contract

- Status: accepted (2026-11-04)
- Date: 2026-11-04
- Component label: Deep (semantics) + Learn (gRPC)
- Decision type: optimal
- Extends: ADR-003

## Context
ADR-003 chose sessions + reads through the log, but did not define the contract. The CLI, the chaos workload and the gRPC server must agree on it, or retries cause double applies that Porcupine rejects (`../02-verification.md`, B4).

## Alternatives considered
| Option | Pros | Cons | Evidence |
|---|---|---|---|
| Client ID: random UUID generated by the client | No extra round trip; stdlib `uuid` (Go 1.27) uses a CSPRNG | Theoretical collision; no server-side expiry | [S1] |
| Client ID: `RegisterClient` through the Raft log | Server-assigned, enables session expiry (dissertation ch. 6) | Extra RPC and log entry; more code | [S2] |
| Many requests in flight per client | Higher throughput | "Last seq + response" dedup becomes wrong; needs a window | [S2] |
| One request in flight per client | Dedup by last seq is correct and simple | Throughput per client is low (fine: workloads use many clients) | [S2] |

## Decision
- **Client ID:** random UUID from stdlib package `uuid` (`uuid.New()`), created once per client process. The generator is **injectable**: the simulator derives IDs from the seeded RNG so runs stay reproducible (ADR-002).
- **One request in flight per client.** Sequence numbers start at 1 and increase by 1 per request. A client retries with the **same** seq until it gets a definite answer.
- **Dedup:** the state machine stores per client `(lastSeq, lastResponse)`. `seq == lastSeq` → return cached response; `seq < lastSeq` → error `STALE_SEQ`; `seq > lastSeq` → apply.
- **Reads:** `Get` goes through the log and carries a seq like writes (simple, one code path).
- **Errors** (gRPC status + details):
  - `NOT_LEADER` + leader hint (node id / address) → client redirects
  - `UNAVAILABLE` (no known leader) → client backs off and tries another node
  - `DEADLINE_EXCEEDED` / connection lost → **outcome unknown**; client retries same seq on any node
  - Pending proposal overwritten (same index, different term) or leadership lost → server returns `NOT_LEADER`; the client retries the same seq, so dedup keeps it exactly-once
- **Missing keys:** `Get` of a missing key → OK with `found=false`; `Delete` of a missing key → OK (idempotent); an empty value is valid and distinct from not-found.
- **Client timing:** deadline 500 ms per attempt; backoff 50 ms doubling to 400 ms with jitter (seeded RNG in the simulator); retry on any node after `UNAVAILABLE`/timeout, on the hinted leader after `NOT_LEADER`.
- **Health:** each node also serves the standard gRPC health service (`grpc.health.v1`), used by Compose healthchecks.
- **Limits:** key ≤ 1 KiB, value ≤ 64 KiB; gRPC max message 4 MiB; AppendEntries ≤ 64 entries / 1 MiB (ADR-001).
- `kv.proto` is drafted at the start of M5 before server code; the same command/response types are used by the simulator from M3.

## Why
- Random 122-bit UUIDs make collisions negligible for test-sized workloads `[source: S1]`, `[source: S3]`
- One-in-flight + same-seq retry is what makes "last seq" dedup correct `[source: S2]`
- Failover as seen by a client ≈ election (300-600 ms) + one deadline (500 ms) + backoff, so < 2 s is plausible locally; CI asserts a looser < 5 s `[assumption: check by M5 smoke test]`

## Cost (what we pay)
- No session expiry: the dedup table grows with the number of clients (acceptable; documented)
- Every read pays log latency (ADR-003)

## Revisit if
- Session table size becomes a problem in long chaos runs → add `RegisterClient` + expiry
