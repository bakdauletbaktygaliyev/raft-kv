## Lesson
### Why this matters in the project
govulncheck tells you if code you actually call (yours, std lib, grpc-go, protobuf later) has a known vulnerability. It matters once dependencies arrive in M5, and a red check after a Go security release is your signal to bump Go. Caching keeps CI fast as the chaos seeds grow.

### Mental model
- **govulncheck** builds a call graph and reports only vulnerabilities in functions your code can reach — fewer false alarms than "this module version has a CVE".
- **CI cache**: each job starts on an empty VM. `actions/setup-go` (cache on by default) restores `GOMODCACHE` (downloaded modules) and `GOCACHE` (compiled packages) from a saved archive keyed by OS + Go version + a hash of `go.sum`, and saves it at the end if the key was new. A second run with the same key skips downloads and recompiles.

### Key concepts
- `go run pkg@vX.Y.Z` builds and runs a tool at a **pinned** version without installing it; the build lands in GOCACHE, so it is cached too.
- Pin versions in CI (`@v1.9.0`, same as local) so a new release doesn't change results unexpectedly; bump on purpose.
- Cache **miss** on the first run ("Cache is not found"), **hit** on the next ("Cache restored from key: …").
- Your first run warned `Cache folder path ... doesn't exist: /home/runner/go/pkg/mod` — no dependencies yet, nothing to download. Harmless.
- Why not `golang/govulncheck-action`: it defaults to Go `stable` and `govulncheck@latest`; a plain step with go.mod's Go and a pinned version is simpler and reproducible.

### Read more
- https://go.dev/doc/tutorial/govulncheck
- https://github.com/actions/setup-go#caching-dependency-files-and-build-outputs

## Pitfalls and common mistakes
- `govulncheck@latest` in CI — unpinned; results can change without a code change.
- Expecting large speedups now: the project is tiny; the gain shows from M5 when grpc/protobuf modules arrive.
- Reading the wrong number: compare the *setup-go* + *vuln* step durations, not the whole job (VM startup dominates).
