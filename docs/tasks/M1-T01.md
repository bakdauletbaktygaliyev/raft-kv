## Lesson
### Why this matters in the project
Every later task (`go test -race`, golangci-lint, CI, the Docker image) assumes one Go version. If your shell, your editor and CI pick different `go` binaries, you get "works on my machine" bugs that look like code bugs. Go 1.24 also lacks features the plan relies on (the module's `go 1.27` line would make 1.24 refuse or try to download a toolchain).

### Mental model
When you type `go`, the shell walks the directories in `$PATH` **left to right** and runs the first `go` it finds. `which -a go` lists *every* match in that order. Having a second `go` later in PATH is harmless today but is a trap: any tool that builds its own PATH (an IDE, a GUI app, a script with a cleaned environment) can end up with the old one.

### Key concepts
- **`$PATH`**: colon-separated list of directories; first match wins.
- **How macOS builds PATH**: `/usr/libexec/path_helper` (run from `/etc/zprofile`) reads `/etc/paths` and then every file in `/etc/paths.d/`. The official Go `.pkg` installer drops a file `/etc/paths.d/go` containing `/usr/local/go/bin`.
- **Package receipts**: `.pkg` installers leave a receipt (`pkgutil --pkgs` → `org.golang.go`). `pkgutil --forget` removes the receipt, not the files.
- **Homebrew Go**: lives in `/opt/homebrew/bin/go`, upgraded with `brew upgrade go`.

### Worked example (what I found on your machine)
```
$ which -a go
/opt/homebrew/bin/go          # 1.27.3  (wins — appears first)
/opt/homebrew/bin/go          # duplicate PATH entry (brew shellenv runs twice in ~/.zprofile)
/usr/local/go/bin/go          # 1.24.12 (old .pkg install)
/opt/homebrew/bin/go
```
Sources: `/etc/paths.d/go` adds `/usr/local/go/bin`; `~/.zprofile` lines 3 and 5 both run `brew shellenv`.

- `man path_helper`

## Task
Remove the old `/usr/local/go` install so that only Homebrew Go 1.27.x remains, then tidy the duplicate `brew shellenv` line.

## Direction
Three things to remove: the directory, the PATH entry file, the package receipt. Then fix `~/.zprofile`. Then open a **new** terminal (PATH is computed at login) and check.

## Pseudocode
```
delete directory  /usr/local/go            (needs sudo)
delete file       /etc/paths.d/go          (needs sudo)
forget receipt    org.golang.go
in ~/.zprofile keep ONE of the two `brew shellenv` lines
open new terminal → which -a go ; go version ; go env GOROOT
```

## Example on a similar problem
Removing an old Python.org install: `sudo rm -rf /Library/Frameworks/Python.framework/Versions/3.9`, `sudo rm /etc/paths.d/...python...`, then `pkgutil --pkgs | grep -i python` and `sudo pkgutil --forget <id>` for each.

## Pitfalls and common mistakes
- Checking in the **same** terminal: the old PATH is still loaded. Open a new one (or `exec zsh -l`).
- `rm -rf` with a typo (`/usr/local /go`) is destructive — paste the path carefully.
- `GOROOT` set by hand somewhere (`~/.zshrc`, `go env -w`) would still point at `/usr/local/go`. `go env GOROOT` should print a path under `/opt/homebrew`.
- VS Code / GoLand may cache the Go path; restart them and check the Go version they report.
