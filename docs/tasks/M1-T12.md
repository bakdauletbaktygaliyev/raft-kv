## Lesson
### Why this matters in the project
The Dockerfile is code too: a bad `COPY`, a Go version bump in go.mod without one in the builder, or a cgo slip would only show up in M5 when Compose fails. Building (and briefly running) the image on every push catches it the same day.

### Mental model
A fourth parallel job: checkout → set up **Buildx** (Docker's BuildKit builder) → build with `docker/build-push-action` (`push: false`, `load: true` so the image is available to later steps) → run the image once as a smoke test.

### Key concepts
- `docker/setup-buildx-action` — creates a BuildKit builder; needed for the GitHub Actions layer cache.
- `cache-from/to: type=gha` — stores Docker layers in the Actions cache (same storage as setup-go's cache). `mode=max` caches the build stage too, not only the final image.
- `push: false` — no registry, no credentials needed; `load: true` puts the image into the runner's local Docker so `docker run` can use it.
- Smoke test: `docker run --rm raftkv:ci --id 1 --peers 1=a:1` must exit 0 — proves the binary actually starts in distroless (catches the cgo/libc failure from M1-T11).
- Checked 2026-11-05: setup-buildx-action v4.4.1, build-push-action v7.4.0.

### Read more
- https://docs.docker.com/build/ci/github-actions/
- https://docs.docker.com/build/cache/backends/gha/

## Task
Add an `image` job to `ci.yml` (given in chat 2026-11-05), push, rerun once to see the layer cache.

## Pitfalls and common mistakes
- Without `load: true` the image exists only in the BuildKit cache; `docker run` fails with "image not found".
- Building without the smoke run: a binary that can't start still "builds" fine.
- Indentation of the new job must match `lint`/`test`/`vuln`.

## How to verify
- [ ] four green jobs: lint, test, vuln, image
- [ ] smoke step prints the config
- [ ] rerun: build log shows `CACHED` layers
