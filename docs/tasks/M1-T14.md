## Lesson
### Why this matters in the project
The Raft core is one big struct whose methods change its state (`Step`, `Tick`, `Advance`). With a value receiver by mistake, the method updates a **copy**: the term or vote you just set silently vanishes. No error, no crash — the kind of bug the chaos tests later find after hours. Knowing the rule cold prevents it.

### Mental model
A method is a function whose first argument is the receiver. Go passes **everything by value** (copies it):
- `func (c Counter) Inc()` → `c` is a copy; changes are lost when the method returns.
- `func (c *Counter) Inc()` → `c` is a copy of the **pointer**; both point at the same struct, so changes stick.

### Key concepts
- Calling convenience: if `c` is an addressable variable, `c.Inc()` works for a pointer method too — Go rewrites it to `(&c).Inc()`. That's why the bug is easy to miss: the call looks the same.
- Rule of thumb: if **any** method needs a pointer receiver, make **all** methods on that type pointer receivers (consistency; method sets matter for interfaces in M1-T17).
- Value receivers are fine for small immutable types (`type Term uint64`, a `Peer{ID, Addr}`).
- Copying a struct copies its fields; a slice or map field still shares the underlying data (M1-T15 covers this trap).
- Constructors usually return a pointer: `func NewCounter() *Counter`.

### Worked example (different type)
```go
type Light struct{ on bool }

func (l Light) TurnOnBroken() { l.on = true }  // sets the copy
func (l *Light) TurnOn()      { l.on = true }  // sets the original

var l Light
l.TurnOnBroken() // l.on == false
l.TurnOn()       // l.on == true  (Go calls (&l).TurnOn())
```

## Direction
Two test functions (or one table with two rows), each: fresh counter → call the method N times → compare `Value()` with what you expect. Add a doc comment to the type and each method saying what it does (for `IncValue`: that it has no effect, and why).

## Pitfalls and common mistakes
- `go vet`/staticcheck may warn that `IncValue` assigns to a field that is never used (`SA4005` "ineffective assignment to field"). That warning **is the lesson** — it's exactly the bug. Silence it with `//nolint:staticcheck // deliberate: value receiver demo` at the end of the **assignment line** inside the method (verified with golangci-lint 2.15.0), so `make lint` stays green.
- Mixing receivers on a real type — don't; this exercise is the only exception.
