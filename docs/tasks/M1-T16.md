## Lesson
### Why this matters in the project
A seed must replay the same run byte for byte. If `raft/` or `sim/` loops over a map (peers, pending requests, in-flight messages) and the order affects what is sent or logged, two runs of one seed differ and the replay is useless. `forbidigo` cannot detect this (it bans names, not `range` over a map), so only the seed-twice hash check catches it, and only after the fact. The habit has to be in your hands.

### Mental model
The spec says map iteration order is **not specified**, and the runtime deliberately varies it so that nobody depends on an order. "Varies" does not mean "shuffled evenly", and that is the dangerous part. Measured on Go 1.27.3, 10,000 loops over one map:

| Keys in the map | Different orders seen | Most common order |
|---|---|---|
| 2 | 2 | 87.5% of loops |
| 5 | 5 | 50% |
| 8 | 8 | 13% |
| 20 | 20 | 22% |
| 100 | 100 | 4.8% |

Only `n` distinct orders appear out of `n!` possible; they look like rotations of one order. So a **small map often looks stable**: three consecutive loops over 5 keys can easily print the same thing. A 3-node peer map would keep the same order most of the time and change it occasionally, which is the worst kind of bug to chase. These numbers are an implementation detail and can change between Go versions; the only guarantee is "no guarantee".

The fix is always the same: take the keys, sort them, then loop over the sorted keys.

### Key concepts
- `maps.Keys(m)` returns an **iterator** (`iter.Seq[K]`), not a slice.
- `slices.Sorted(iter)` collects an iterator into a sorted slice. Together: `slices.Sorted(maps.Keys(m))`.
- `fmt.Println(m)` prints maps in sorted key order, so printing a map can hide the problem. Loop to see it.
- Reading or writing a single key (`m[k]`) is always fine. Only **iteration** is random.
- Order-independent loops (summing values, counting) are safe, but sorted is the safer default in deterministic packages.

### Worked example (different data, output checked with Go 1.27)
```go
scores := map[string]int{"ann": 3, "bob": 1, "cid": 2, "dan": 5, "eve": 4}

for k := range scores { ... }             // order not guaranteed; may repeat, then change

for _, k := range slices.Sorted(maps.Keys(scores)) {
	fmt.Println(k, scores[k])             // always ann, bob, cid, dan, eve
}
```

## Task
In `warmup/maps/` (package name `maporder`) write, **yourself** (Learn task):
- `RawKeys(m map[string]int) []string`: appends keys in `range` order
- `SortedKeys(m map[string]int) []string`: returns them sorted

and tests:
- `TestRawKeysOrderVaries`: calls `RawKeys` many times and shows at least two different orders appear
- `TestSortedKeysStable`: calls `SortedKeys` many times and shows every result equals the expected slice

## Direction
Two calls match about half the time with 5 keys (see the table), so a single comparison proves nothing. Loop (say 100 times) and stop as soon as one result differs from the first; fail only if none ever did. Use at least 5 keys.

## Pitfalls and common mistakes
- A test that needs randomness to pass could be flaky. With 5 keys and 100 tries a false failure is practically impossible (about 0.5^99), but it is still a test about the runtime, not your code. It belongs in a warm-up, never in `raft/`.
- `fmt.Println(m)` sorts keys, so it won't show the variation.
- `maps.Keys` returns an iterator: `len(maps.Keys(m))` does not compile.
- The standard packages are named `maps` and `slices`, hence the package name `maporder` for this folder.
