## Lesson
### Why this matters in the project
The module path is the import prefix for every package (`.../raft-kv/raft`, `.../raft-kv/sim`). Changing it later means rewriting every import, so pick the final GitHub path now.

### Mental model
A **module** is a tree of packages with a `go.mod` at its root. `go.mod` says: my name (module path), which Go language version I need (`go 1.27`), and which dependencies (added later by `go get`/`go mod tidy`). `go.sum` appears once there are dependencies and holds their checksums; both files are committed.

### Key concepts
- **Module path** = where it would be fetched from: `github.com/bakdauletbaktygaliyev/raft-kv`.
- **`go` directive**: minimum language version; `go mod init` writes the current one (`go 1.27.3`). The card asks for `go 1.27` — either is fine; `go mod edit -go=1.27` sets it.
- **`.gitignore`** for this project: build output (`/bin/`), coverage files (`*.out`, `coverage.html`), test artifacts (`/testdata/out/`, Porcupine `*.html` you generate), editor dirs (`.idea/`, `.vscode/`), `.DS_Store`.
- `docs/` already exists and should be part of the first commit.

### Worked example
```
$ go mod init example.com/hello
go: creating new go.mod: module example.com/hello
$ cat go.mod
module example.com/hello

go 1.27.3
```

## Pitfalls and common mistakes
- Running `go mod init` inside `docs/` creates the module in the wrong place.
- Module path typos/capital letters: GitHub usernames are case-insensitive, Go module paths are not.
- Committing `.DS_Store` — add it to `.gitignore` before the first `git add`.
